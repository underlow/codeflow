Review whether the current plan can deliver the agreed behavior without making
a developer invent a product or binding design decision. Inspect the complete
plan and any task files before implementation. A small plan may have no separate
task files; judge whether its instructions are sufficient for its actual scope.

Check that every required result is assigned to work, dependencies arrive before
they are needed, shared data and behavior agree between tasks, and the results
join through the application's real entry paths. Check important failures,
recovery, compatibility, and integration. Named verification must be executable,
state an expected observation from the contract, and catch a plausible harmful
mistake. Verify important statements about the existing repository in code.
When a gap affects shared work, inspect all dependent tasks rather than only the
first one. Finish the whole plan before reporting.

Use requirements for behavior and scope; use agreed design for binding technical
choices. Report contradictions or missing consequential decisions, not a private
implementation detail the developer can choose. Do not require pseudocode,
helper organization, copied requirements, or detailed test bodies. A plan need
not prescribe every edit, but its developer must know the result to deliver.

Follow the common review contract. Return concrete findings and limitations in
the final response. Do not edit the plan or contract, implement code, commit, or
launch agents.
